# Deploying GroundedTriage (P8.2)

The supported cloud target is **Render**, using native Go and Python runtimes (no Docker) and **Supabase** as the database. Everything is described by `render.yaml` in the repo root.

| Service | Render type | What it runs |
|---|---|---|
| `groundedtriage-api` | web (public, HTTPS) | `cmd/api`: REST API + agent review UI + dashboard |
| `groundedtriage-worker` | background worker | `cmd/worker`: poll → classify → route → escalate → meetings → replies → outbound → monitoring |
| `groundedtriage-ml` | private service (no public URL) | `ml-service` (FastAPI): classification cascade, retrieval, drafting, faithfulness gate |

The ml-service has no authentication of its own. It is a **private service**, so only the api and the worker (on Render's private network) can reach it. Never change it to a web service.

## 1. Before the first deploy (from your laptop)

1. **Supabase.**
   - Use the *Session pooler* connection string (port 5432), as in `.env.example`.
   - Apply the schema and verify it:

     ```sh
     make migrate && make migrate-verify
     ```

     The api can't migrate on start, and a pre-deploy command needs a paid plan, so run migrations from your machine before deploying a version that adds one.
2. **Knowledge base.** Run `make kb` once against the same `DATABASE_URL`. This was already done for the Mumbai project (6,221 documents, 13,220 chunks).
3. **Model bundle.** The deployed ml-service gets its models from a URL, because `models/` is gitignored.

   ```sh
   make models-pack ARGS="fast_tier spam_filter"            # CPU-only profile (6.5 MB)
   make models-pack ARGS="fast_tier spam_filter deep_tier urgency"   # once Arya's models exist
   ```

   - The command prints `MODELS_SHA256=…`.
   - Upload `models-bundle.tar.gz` to any HTTPS location the service can download without credentials, for example a GitHub release asset.
   - The bundle contains only the model files, but treat the URL as semi-private.
   - The ml-service checks the sha256 before extracting. A wrong or changed file is refused and nothing is installed.
4. **Push the repo** to GitHub (Arya pushes; Claude never does).

## 2. Create the Blueprint

1. Render dashboard → **New → Blueprint** → pick the repo. Render reads `render.yaml`.
2. Fill in the values marked `sync: false`:

   | Key | Where | Value |
   |---|---|---|
   | `DATABASE_URL` | group `groundedtriage-shared` | Supabase Session pooler string |
   | `GROQ_API_KEY` | group `groundedtriage-shared` | Groq key (drafting, meeting extraction, judge) |
   | `MODELS_URL` | `groundedtriage-ml` | HTTPS URL of `models-bundle.tar.gz` (empty = no models) |
   | `MODELS_SHA256` | `groundedtriage-ml` | the sha256 printed by `make models-pack` |

   `API_KEY` is **generated by Render** (`generateValue`). Copy it from the api service's *Environment* page and give it only to the agents who need it.
3. Deploy. The ml-service build installs CPU-only torch, fetches the bundle and pre-downloads bge-small, which takes several minutes. The Go builds take about a minute each.
4. Check:

   ```sh
   curl https://<api-host>/health      # status ok, ml_service with models_loaded
   curl -H "X-API-Key: $API_KEY" "https://<api-host>/tickets?limit=5"
   ```

   Then open `https://<api-host>/`, enter the key, and follow the manual UI test in `CLAUDE.md` §2.

## 3. Security settings (Phase 6 review)

- **HTTPS only.** Render terminates TLS. `REQUIRE_HTTPS=true` on the api redirects any request that arrived over plain HTTP (`X-Forwarded-Proto: http`) to https with a 308, and sends `Strict-Transport-Security` on every response. The UI's CSP, `nosniff` and `no-referrer` headers apply as they do locally.
- **The API key is never in page source or the JS bundle.** The agent types it into the UI; it lives only in that browser's localStorage and is sent as `X-API-Key`. The api refuses to start without a key, or with the `.env.example` placeholder.
- **Rotation:** change `API_KEY` on the api service (Environment → edit, or *Generate* again) and redeploy.
  - Every browser then gets a 401 and is sent back to the key prompt; give the new key to the agents.
  - Locally, change `API_KEY` in `.env` and restart `make api`.
  - Rotate after anyone who knew the key leaves, and whenever it may have been shared in a screenshot or chat.
- **One shared key** is the capstone's access model. Per-user accounts and RBAC are future work (CLAUDE.md §3c).
- **Secrets** stay in Render's environment, never in `render.yaml`. `make render-validate` fails if a secret-looking key gets an inline value.

## 4. CPU-only profile (fast tier only)

The Blueprint is the CPU-only profile: `TORCH_DEVICE=cpu`, `MODEL_FP16=false`, and torch from the CPU wheel index. With a bundle that holds only `fast_tier` + `spam_filter`:

- **Classification:**
  - the spam filter, then the TF-IDF fast tier;
  - with no deep tier, tickets under τ get `low_confidence=true`, and the routing rules send them to `human_review`;
  - urgency comes from the documented heuristic (`urgency_source=heuristic`).
- **Grounded replies** work fully. They need the bge-small embedder (downloaded at build time into `ml-service/.hf`), Supabase and Groq.
- `/health` shows `models_loaded.deep_tier=false` and `urgency=false`. The dashboard's *Models loaded* tile reads `fast_tier`.
- **Adding the fine-tuned models later:**
  - re-pack with `deep_tier urgency` and upload the new bundle;
  - update `MODELS_URL` and `MODELS_SHA256`, then redeploy the ml-service.
  - `fetch` replaces whole artifact directories, so a new bundle never mixes with old files.
  - The DeBERTa deep tier (~0.7 GB) plus torch fits the `standard` plan (2 GB) on CPU, but slowly. Measure before relying on it.

## 5. Cost and plans

Render's free plan covers web services only, so the worker and the private service need paid plans. The Blueprint uses:

- api: `starter`;
- worker: `starter`;
- ml: `standard`, because torch, bge-small, the fast tier and the spam filter need more than the 512 MB of `starter`.

Check Render's current prices before deploying. Supabase stays on its free tier: the database is about 78 MB of 500 MB, and a free project pauses after inactivity (resume it in the dashboard). Groq's free tier caps gpt-oss-120b at 200k tokens a day; one grounded draft costs about 4–5k tokens.

## 6. Validation and what is not verified

- `make render-validate` validates `render.yaml` against Render's published JSON schema (`https://render.com/schema/render.yaml.json`), then checks that:
  - every `fromService` reference points at an existing service;
  - no secret has an inline value;
  - every `./cmd/...` in a command exists;
  - no worker or private service is on the free plan.

  Result on 2026-10-17: *valid, 3 services; repo checks passed*.
- **Not verified, because nothing has been deployed:**
  - an actual Render deploy;
  - Render's Go version support for `go 1.26.0` in `go.mod` (if the build reports an unsupported version, set a `GO_VERSION` the platform supports, or lower the `go` line);
  - the build-time bge-small download;
  - ml-service memory under the `standard` plan.
- **Optional containers:** `docker-compose.yml`, with `deploy/go.Dockerfile` and `deploy/ml.Dockerfile`, runs the same three services against Supabase (no local Postgres). It is **not verified**, because the Docker daemon wasn't running on the dev Mac (8 GB RAM, with an evaluation in progress). Nothing else in the repo depends on Docker.
