## 1. Scope and taxonomy

- **6 support-triage categories** (P2.1 review, supersedes BUILDPROMPT's 11 = SCRIBE's 6 — Work, Spam, Personal, Urgent, General, Meeting Scheduling — plus 5 support categories). Since the Phase 3 review these are 5 topic classes plus Spam from a binary filter (below): Technical Issue, Billing, Feature Request, General Inquiry, Spam, Meeting Scheduling.
  - Dropped: Work and Personal (not support topics, no clean labels); Urgent (urgency is its own axis); Complaint (a tone/escalation signal, not a topic); Account/Access (no clean labels; folded into Technical Issue). Rationale: avoid evaluating mostly on synthetic data.
  - The SCRIBE baseline is evaluated on the same 6 classes via the zero-shot descriptions in `taxonomy.yaml`; its regex rules still cover Spam and Meeting Scheduling. **The report must state this.**
  - Sample CSV labels remapped: Account/Access→Technical Issue; Complaint, Personal, Work and General→General Inquiry; Urgent→Technical Issue for the DB-down alert, otherwise General Inquiry.
- **Two tasks since the Phase 3 review:** a binary **spam filter** plus a **5-class topic classifier** (no Spam). `config/taxonomy.yaml` has `filter_categories: [Spam]`; `app.taxonomy.topic_categories()` (5) / `filter_categories()`. The contract is unchanged: `Classification.category` can still be Spam, set by the filter with `tier="spam_filter"`.
- **Urgency** is trained and evaluated on low/medium/high only; "critical" comes only from documented heuristic rules. Neither dataset has English critical rows.
- **Documented deviation from SCRIBE (Phase 0 review):** `openai/gpt-oss-120b` (Groq) is the LLM for BOTH the SCRIBE baseline's draft→refine and this system's generator. SCRIBE used LLaMA-3-70B, which isn't available on the Groq key (404). The same LLM on both sides isolates the effect of grounding in P7.2. Must be stated in `results/REPORT.md`. Optional P7 extra: a LLaMA-70B baseline via another OpenAI-compatible provider if one is free (why `GROQ_BASE_URL` is configurable).
- **The style shortcut is a first-class finding for the report** (Phase 3 review): see section 6 and results.md.

## 2. Infrastructure, config and tooling

- **No `.env` in make** (P0.1a): make parsed it as Makefile syntax, which breaks on `$`, `#` and URL-encoded passwords. Each program loads `.env` itself: Go via godotenv, Python via python-dotenv / pydantic-settings (pytest's conftest loads it too), honcho for `make dev`. Shell sourcing (`set -a; . ./.env`) was rejected: it expands unquoted `$` and breaks on `&`/`;`. Values containing `$` go in single quotes, which all three loaders treat literally.
- **Dependencies:** ruff/pytest/honcho live in `ml-service/.venv` as `[dev]` extras, called via `.venv/bin/`. Runtime deps are added by the part that first needs them (keeps `make setup` light on 8 GB). Heavy ML deps (torch, transformers) are optional extras (`[models]`, `[baseline]`). torch is imported lazily (`app.device.select_device` → `cpu` with a log when missing); `/health` only probes `find_spec("torch")`.
- **Go:** module `github.com/RishabhWDB/GroundedTriage`; `go.mod` says `go 1.26.0` (raised by pgx v5.11 / goose v3.29; GOTOOLCHAIN=auto downloads it). Contract structs live in `internal/model` to avoid import cycles between ingest, store and pipeline.
- **Tests:** slow tests skipped unless `RUN_SLOW=1`; integration tests skipped without `TEST_DATABASE_URL` (both in `ml-service/tests/conftest.py`). Go build tag `live` = needs running services (excluded from `make test` and `make test-integration`). Integration tests share one migrated schema per package (`TestMain` → `storetest.Run`) and isolate rows with `storetest.UniqueID` or `testDB.Truncate` (refuses non-`test_` schemas). The per-package setup cost is accepted (Phase 0 review). The TestClient/httpx2 deprecation warning is left alone.
- **Worker/API stubs:** the worker blocks until SIGINT/SIGTERM because honcho stops every process when one exits. The api's `/health` calls the ml-service with no retries and a 3 s timeout and reports `"unreachable"` rather than failing.
- **Memory and crash safety (2026-10-17 OOM reboot):** see CLAUDE.md for the rules. `scripts/jobguard.py`: flock `datasets/raw/.jobguard.lock`; refuses on `kern.memorystatus_vm_pressure_level` ≥ 2 or `memory_pressure -Q` free < `JOBGUARD_MIN_FREE_PCT` (20), or while `uvicorn app.main`/`honcho start` runs (unless `--allow-services`); job in its own process group, leftovers SIGTERM then SIGKILL; peak RSS (`RUSAGE_CHILDREN`) + swap to `datasets/raw/jobguard.jsonl`; exit 75 on refusal. `dev`/`ml`/`demo` use `--check-only --allow-services`. `app/fileio.py`: unique temp in the same dir + fsync + `os.replace` + dir fsync for whole files; fsync per row and truncated-last-line tolerance for append-only JSONL. Model artifacts and `results/*.json` are not atomic (regenerable; loaders reject corrupt artifacts).

## 3. Database

- Supabase Postgres in **ap-south-1 (Mumbai)**, Session pooler (`aws-0-ap-south-1.pooler.supabase.com:5432`) for both DATABASE_URL and TEST_DATABASE_URL. The old Sydney project is Arya's to delete.
- **Migrations:** goose v3, SQL embedded via `migrations/embed.go`, run by `cmd/migrate` (no CLI to install). Only `up` and `status` (+ read-only `verify`) are exposed; down-migrations are unreachable. golang-migrate was considered; goose's embed + Provider API is simpler. Each file runs in a transaction; `DO $$ … $$` blocks need `-- +goose StatementBegin/End`.
- **Schema choices:** kb ids are text (`kb_documents.id` = source doc id, `kb_chunks.id` = stable chunk id), so citations are `text[]`; every table has a uuid/identity PK plus `created_at`; `classifications` keeps history (no unique `ticket_id`) and has `low_confidence`; the embedding dimension is fixed at 384 in SQL (a new embedding model needs a migration).
- **search_path:** every Go connection runs `SET search_path TO [<test schema>,] public, extensions` in AfterConnect (`store.SearchPath`); Python psycopg connections do the same. The Supabase role default isn't relied on. `TestCosineQueryResolvesVector` guards it.
- **Dropped connections (P7.2c):** a long P7.2 run hung ~47 min in psycopg `poll` on a connection the pooler had silently dropped. `rag.kb.connect` sets TCP keepalives (idle 30 s, 3 × 10 s), `connect_timeout` 15 s, `statement_timeout` 120 s; `Retriever` takes a `reconnect` callable and retries once on `OperationalError`/`InterfaceError` (ml-service registry and the eval).
- **Mumbai demo rows:** 20 `csv/accepted` + 1 `csv/skipped/non_english` sample tickets (seeded by the worker; csv checkpoint 2026-10-09T06:00Z). Reviews said to leave them as they are, so pipeline steps were tested on TEST_DATABASE_URL, not DATABASE_URL. All migrations through 00012 are applied there (all additive).

## 4. Ingestion

- **Sources** (P1.1): each source's `Name()` is its type (`csv`/`email`/`zendesk`) = `Ticket.Source`. At most one enabled source per type, so outbound resolves the reply adapter from `Ticket.Source` alone (two instances of a type would need a `source_instance` column; out of scope). `config/sources.yaml` holds non-secret options only; adapters read credentials from env; unknown keys rejected (`KnownFields`); disabled entries need no factory.
- **CSV** (P1.2): `external_id` = `Id` column, else `csv-` + 16 hex of sha256(sender, subject, body, date) (stable across reorders; same text with different dates stays distinct). `ReceivedAt` from `Date` (RFC 3339 / `YYYY-MM-DD[ HH:MM:SS]`, UTC), else file mtime. `Label` isn't in the contract (exposed via `CSVSource.ReadRows()` for eval). `datasets/sample_emails.csv` adds an optional `Date` column and deliberate edge cases: a repeated complaint with a different date, a Portuguese billing email, `noreply@`/newsletter/automated senders, an HTML body, a quoted reply and a signature.
- **Email parsing** (P1.3a): `emersion/go-message` (RFC 2047, transfer encodings, charsets). `ExternalID` = Message-ID without brackets, else a `nomsgid-` content hash. `ThreadID` = References[0], else In-Reply-To, else own Message-ID. text/plain preferred; attachments ignored.
- **Cleaning** (P1.3a, P1.5): `preprocess.CleanBody` is the one idempotent chain for all adapters: HTML→text (drops `<blockquote>`, `.gmail_quote`, Outlook `#appendonsend`/`#divRplyFwdMsg`), quote stripping (first "On … wrote:" even when wrapped, Outlook `From:`+`Sent:/To:/Date:` blocks, underscore rules, "-----Original Message-----", every `>` line), signature stripping (RFC 3676 `-- `, mobile footers), whitespace/NFC/zero-width removal. Sign-offs like "Thanks, Priya" are kept. If stripping leaves nothing, the original is kept.
- **IMAP/SMTP** (P1.3b): a connection per poll, mailbox SELECTed read-only, UNSEEN SINCE the day of `since`, `BODY.PEEK[]` so **inbox flags never change**. `ReceivedAt` = INTERNALDATE, else `Date`. Mail from our own `SMTP_FROM` is skipped (reply loops); unparseable messages are logged and skipped. Replies: text/plain UTF-8 quoted-printable, `In-Reply-To` + `References`, CR/LF stripped from headers, no double "Re:", `nomsgid-` ids never used as In-Reply-To.
- **Zendesk** (P1.4): `GET /api/v2/incremental/tickets/cursor.json?start_time=…&include=users`, following `after_cursor` until `end_of_stream`, ≤ 50 pages per poll. `start_time` clamped to ≤ now−61 s; zero `since` looks back 30 days. Only new/open/pending/hold. `ExternalID`=`ThreadID`=ticket id; `Body`=description; `Sender`=requester email or `zendesk-user:<id>`; `ReceivedAt`=`created_at`. **Limitation:** follow-up comments aren't ingested. Retries: 429 always (honours `Retry-After`, else 2^n s, ≤ 5); 5xx/transport only for GET — a failed reply PUT is never retried (it may have posted). Freshdesk not implemented.
- **Normalisation and dedupe** (P1.5, P1.7): sender normalised by `preprocess.NormalizeSender` (`net/mail` → bare lower-cased address; `zendesk-user:42`-style values trimmed/lower-cased). `content_hash` = sha256(sender, subject without Re:/Fwd:/AW:/WG: lower-cased whitespace-collapsed, body lower-cased whitespace-collapsed); the sender is included so two customers sending the same text aren't merged. Duplicates by `(source, external_id)` or content hash are rejected (`duplicate_content`); check-then-insert isn't atomic, safe with a single ingestion worker.
- **Language** (P1.5, P1.7): `abadojack/whatlanggo` (lingua-go rejected for RAM). Skipped as `non_english` only when detection is reliable, not English, and ≥ 30 letters. **Non-English tickets are stored** with `ingest_status='skipped'`, `skip_reason='non_english'` (named `ingest_status` to avoid confusion with route/draft status); empty tickets are dropped. Only `accepted` tickets are classified; skipped ones route to a human queue.
- **Polling** (P1.6): fetch with `since = checkpoint − 10 min`, then set the checkpoint to the max fetched `ReceivedAt` (never "now"). A failing source is logged + audited (`ingest.error`), doesn't stop others, and keeps its checkpoint. One `ingest.poll` audit row per source and poll (counts + up to 100 ids; no per-ticket row, each would cost a round-trip). A poll in progress at SIGTERM finishes (≤ `PollTimeout` 5 min). Ingestion does 2 queries per ticket; batching deferred.

## 5. Data and splits

- **Sources:** Tobi-Bueck (HF parquet, EN only); SpamAssassin public corpus (`20030228_spam` + `20050311_spam_2`; ham from `20030228_easy_ham`, `_easy_ham_2`, `_hard_ham`); ~400 synthetic meeting requests. `albertobircoci/support-ticket-priority-dataset-50k` was **dropped** (no text column; priority exactly 50/35/15%, no critical).
- **Tobi-Bueck mapping** (first match, in `taxonomy.yaml`): type=Change → Feature Request; Billing and Payments, Returns and Exchanges → Billing; Technical/Product/IT Support, Service Outages and Maintenance → Technical Issue; General Inquiry, Sales and Pre-Sales, Customer Service → General Inquiry; Human Resources → dropped (HR with type=Change, 39 rows, become Feature Request). Priority very_low/low→low, medium, high, critical. Build: 61,765 → 28,261 EN → 514 HR dropped, 1 empty, 4,518 duplicate bodies → **23,228 rows** (raw sha256 `1e2de97c…71a9`). Dedupe key = lower-cased whitespace-collapsed body (first kept). Anonymisation placeholders (`<tel_num>`, `<acc_num>`, `<name>`) kept; literal `\n` becomes a newline.
- **SpamAssassin:** no formal licence (offered "as a service to spam filter developers"; copyright with senders) → downloaded by script, never committed or redistributed; cite the Apache SpamAssassin project. Chosen over Enron-Spam for provenance and RFC 822 format. Archives are untrusted: read from the tar stream in memory, never extracted. Spam: 1,896 → 27 too short / 69 non-English / 247 duplicates → **1,553 rows** (127 truncated to 4,000 chars); 2002–2005 era. Ham: 4,150 → **4,089 rows** (ids `sah-*`, no category). Spam/ham rows have no urgency label.
- **Synthetic meetings** (P2.1e): gpt-oss-120b, temperature 0.9, JSON mode, reasoning low, 5 per call (80 batches, 80,308 tokens). Specs from `random.Random(42)` over committed option lists; prompt in the module; responses cached in `datasets/raw/llm_cache/synthetic_meetings/`. **Final rows committed** (`datasets/synthetic/`; a re-run wouldn't reproduce them). Checks: 400 unique bodies, 0 placeholders, 97% mention a meeting word, 323 unique subjects. **Caveat for the report:** shorter than Tobi-Bueck (median 260 vs 374 chars) with keyword-heavy subjects, so the class is likely easier; report per origin. Urgency NA.
- **Every row carries `origin`** (real | synthetic | augmented); metrics are reported overall, real-only and per origin.
- **Model input:** the `text` column = `app/textinput.model_input` (subject + blank line + body); serving must use the same function.
- **Group-aware split** (P2.1h, extended in P3.7): near-duplicates (word-unigram TF-IDF fitted on all rows, cosine > 0.9; unigrams make it an upper bound) are linked into connected components; every group stays in one split. Per label × origin stratum: shuffle groups (seed 42), largest first, each to the split furthest below its target (70/15/15). Groups keyed by smallest id (input-order independent). **Each stratum has its own RNG** (seed + hash of the stratum), so adding a stratum never reshuffles others. Finding: before grouping, 11.6% of test rows had a near-duplicate in train (genuine LLM paraphrases in Tobi-Bueck) and inflated val macro-F1 (0.825 → 0.802 after the fix).
- **Two-task rebuild (P3.7, current):** corpus Tobi-Bueck 23,228 + spam 1,553 + ham 4,089 + meetings 400 − 18 cross-source duplicates = 29,252 rows; 1,862 near-dup groups (4,328 rows, largest 14). One assignment, stratified by label × origin (label = category or "Ham"); both tasks are cut from it, so a row in one task's train is never in the other's val/test.
  - **Topic:** 5 classes; train cap = 5 × the smallest **real** topic class (Feature Request 1,743) = **8,715**, so only Technical Issue is cut. Train 15,910 / val 3,545 / test 3,545. Synthetic rows never set the cap. val/test are never resampled.
  - **`train_urgency`** = every uncapped train row with an urgency label (16,258), from the same pre-cap pool (no overlap with val/test).
  - **Spam task:** every row of each split, topic tickets uncapped: `spam_train` = 1,076 spam vs 2,862 ham + 16,258 Tobi-Bueck + 280 meeting (+ style-aug negatives, below); `spam_val`/`spam_test` = 230 spam vs 613 ham + 3,485 + 60 each.
  - Imbalance is handled by **class weighting, not more downsampling**: fast tier `class_weight="balanced"`, deep tier class-weighted CE (`w_c = N/(K·n_c)`), checkpoints selected on **val macro-F1** (`docs/model_artifacts.md`).
  - **Identify data by the test content hash in the export name, not the archive hash** (the archive bundles docs that change). Current: test content `e2552b04338b4d5872aab17662d750294ce894602f3de0752b90c5049e3d0e81` → `datasets/export/groundedtriage-splits-e2552b04338b.tar.gz`; spam_test `e6997f05…3272`. **Archives `c6539fff94a1` and `db976b0585b2` are stale (6-class) and must not be used.** Rebuilds are byte-identical.
- **Data audit** (`make data-audit`): 0 cross-split near-duplicate pairs (train-pool~val, ~test, val~test) for both tasks. Shortcut check: Meeting Scheduling is separable from the subject alone (F1 0.99) or body alone (1.00), so neutralising subjects wouldn't help; Spam near 1.0 too.
- **Stress set** (P2.1i): 100 rows, gpt-oss-120b (temperature 0.9), seed 1337 and its own prompt: 50 `embedded_meeting` (a technical/billing problem whose main ask is a meeting) + 50 `call_mention` (mentions calls/Zoom/demos but no meeting ask). Columns `intended_category`, `category` (editable), `needs_review`, `reviewer_notes`. **Eval only, never trained on, not in the export; no number reported until every row is reviewed** (`load_reviewed()` enforces). Also tracked: real test tickets matching `MEETING_WORDS` that aren't Meeting (the regex also matches "call 1-888…" in spam).
- **Style augmentation** (P3.8): 25% of each class of capped topic `train` (seed 2026) = **3,978 rows**, shuffled so any prefix is stratified. Prompt fixed in the module (same request, product, facts; placeholders replaced with invented values; no stock phrases); seeded style spec per row (register 6, length 2, greeting 5, typos 3, subject style 3). gpt-oss-120b, temperature 0.9, JSON mode, 8 per call, cached by request sha256. Rejected when too short, placeholder left, or body cosine > 0.9 to the source **body** (`--recheck` re-applies). Rows: `id = aug-<source id>`, `aug_of`, source labels, `origin=augmented`. `data.build` keeps rows whose source is in the current train and checks labels. ~450 tokens per row → ~9 days at the free cap. Exported as optional `train_style_aug` (Arya trains with and without it).
- **Style-aug rows as spam negatives** (P3.14): `add_aug_negatives` appends `train_style_aug` (`is_spam=false`, `source_dataset=style_aug`) to `spam_train` only; every aug row paraphrases a topic train row, so no leakage; spam_val/test unchanged.
- **Kaggle** (P2.1a): new-style token (`KGAT_…`) in `KAGGLE_API_TOKEN`, read natively by `kaggle` 2.2.4. `import kaggle` authenticates at import and `exit(1)`s on failure, so `data.kaggle_auth` loads `.env` first, imports lazily, silences the SDK and raises `KaggleAuthError` with fix-it steps; it diagnoses malformed tokens without printing them.

## 6. Classification

- **Source-style shortcut (P3.5a, the reason for the two-task design):** on the 22 hand-written samples the old 6-class fast tier predicted Spam for 13 ("API returning 500 errors" → Spam 0.96). Spam was SpamAssassin, the only *human-written* class; the other real classes were Tobi-Bueck's formal LLM-written tickets, so "informal human English" ≈ Spam. val/test can't show it (source and class coincide).
- **Style dependence beyond Spam (P3.12):** with Spam removed, human text falls into Technical Issue (49 of 59 preliminary Twitter rows). TF-IDF features learned on LLM style don't transfer; the deep tier (pretrained DeBERTa) and full style augmentation are the remedies, and both must pass `make ood-eval`.
- **Fast tier** (P3.1, P3.12): word 1–2-gram TF-IDF (min_df 2, ≤200k) ∪ char_wb 3–5 (min_df 3, ≤300k), sublinear tf, float32; LR `class_weight="balanced"`, lbfgs. C from {1, 4, 16, 64} by val macro-F1 (C=64; 16 within 0.001). **Calibration ∈ {none, sigmoid, isotonic} chosen by val macro-F1, ECE as tie-break: none wins** — CalibratedClassifierCV fitted on capped-train CV predictions learned train's priors and collapsed General Inquiry (sigmoid 0.703, isotonic 0.687 vs 0.823), and the plain LR is better calibrated anyway (ECE 0.070). Version stamp `fast-<UTC yyyymmddHHMMSS>-<train content sha[:8]>`. The artifact is a joblib pickle: only load models this repo trained; `FastTier.load` returns None (logged) on missing/unreadable files or wrong classes and warns on a scikit-learn version mismatch.
- **Embedding fast tier** (P3.13, comparison only, no decision): bge-small-en-v1.5, CLS + L2, 256 tokens, fp16 on MPS; embeddings cached by sha256(model | max_length | text) in `datasets/raw/emb_cache/*.npz`; balanced LR, C from {0.25…64} by val macro-F1 (C=16), uncalibrated.
- **Deep tier / urgency loader** (P3.2, `triage/hf_model.py`): **validation at construction, weights at first use.** Required `config.json`, `label_map.json`, `model_card.json`, `model.safetensors`, `tokenizer.json` or `tokenizer_config.json`; label_map ids exactly 0..n-1, no duplicates; the deep tier's labels must be exactly the **5 topic classes** (6-class maps rejected since P3.10; any id order); model_card needs the right `task`, positive int `max_length`, `val_metrics.macro_f1`; `num_labels` must match. Any failure → `available=False` with a logged reason, never raised; a failure at weight load also flips it and callers fall back. Inference: AutoTokenizer + AutoModelForSequenceClassification, **fp16 on MPS** (`MODEL_FP16`; CPU fp32), `inference_mode`, batches of 16, truncation to `max_length`, softmax in fp32; one model per role stays resident.
- **Cascade** (P3.4): spam filter first (below); fast tier on every remaining ticket; confidence **< τ** → deep tier when available (one batch), else keep fast with `low_confidence=true` (also when the deep tier fails at load). Urgency on every ticket. `model_versions` = fast_tier, tau, deep_tier (if available), urgency (version or "heuristic"), spam_filter. **τ = 0.7 is an untuned default** (`config/cascade.yaml`, `tuned: false`). **τ rule** (`make tune-tau`): sweep 0.00–1.00 step 0.01 on val; smallest deep-tier share whose macro-F1 is within 0.005 of the best; ties → smaller τ; writes τ, rule, val numbers and both versions. Without a valid deep tier it changes nothing and exits 0 (no fake curve). Serving: `app/models.Registry` once per process; fast tier loads on first `/classify`; `/classify` returns 503 "run `make fast-tier`" without it; τ re-read from YAML per request. `Cascade.classify` also implements `app.interfaces.TicketClassifier` for P7.
- **Urgency** (P3.3): model label_map exactly `[low, medium, high]` (optionally + `critical`). **Heuristic** (`triage/urgency.py`): six regex groups counted once each — urgency keywords +3, deadline +1, escalation +1, negative +1, business impact +2, low-urgency cues −2; ≤ −1 → low, 0..2 → medium, ≥ 3 → high. **critical = business impact AND (urgency keywords OR escalation)**, applied on top of the model too (marked `urgency_source="heuristic"`). Heuristic confidence 0.4 + 0.1 per group (max 0.8), uncalibrated. Cue lists written before the val run and never tuned on val (the +2→+3 keyword change was a design fix from a toy example). Model load failure → heuristic for that and later calls. Ordinal metrics: macro-F1 over low/medium/high + MAE on low<medium<high<critical + share off by ≥ 2.
- **Spam filter** (P3.9, P3.10, P3.12, P3.14): same features as the fast tier, binary balanced LR, no calibration; C from {1, 4, 16} by val average precision (16). Scores are float64 (float32 made a threshold miss by one ticket). Two stored threshold rules, chosen on spam_val:
  - `support`: mute = lowest score with support-ticket FPR ≤ 1%; review = support FPR ≤ 5%. It mutes ~20% of ham (human mail), because LLM-written support tickets all score near 0.
  - **`support_and_ham` (default, `SPAM_RULE`, card `default_rule`; chosen on val + ood-dev in P3.12):** the same limits on support **and** ham. Reviewed ood-dev: mutes 0/9 sample emails (vs 6/9) and caught 7/8 Enron spam (vs 8/8) before P3.14.
  - In the cascade: ≥ mute → `Spam`, `tier=spam_filter`, confidence = score, topic models skipped; review band → topic as usual + **`possible_spam=true`** (routed to review, never muted); without `models/spam_filter/` nothing is Spam, `spam_score` null, version "absent". Version string includes the rule.
  - Contract: `Tier` adds `spam_filter`; `spam_score` (0–1, nullable), `possible_spam` (bool); migration 00005.
  - P3.14 trade-off (aug negatives): ood-dev Enron spam caught 7/8 → 4/8 (Enron's lower-cased tokenised text looks like informal negatives); muted Twitter rows 7 → 2. Thresholds re-derived by the same rules; final decision in Phase 7.
- **Go classify step** (P3.5): only `ingest_status='accepted'` tickets with no classification; ≤ 100 per run (`BatchSize`), oldest first, one request per ticket. A failed ticket (transport, non-2xx after retries, mismatched `ticket_id`, unknown category) stays unclassified for the next run; **3 consecutive failures stop the run** (`ErrMLUnavailable`). One `classify.run` audit row per run. `worker -once` exits 1 on failure.

## 7. Evaluation protocol

- **Reporting rule:** macro-F1 is the headline; accuracy secondary (Technical Issue dominates test). Always overall, real-only and per origin. Topic reports average over the 5 topic classes (averaging in a support-0 class under-reports macro-F1).
- **Selection discipline:** every choice (variants, thresholds, rules, τ) is made on val + **ood-dev** only. Test is untouched until P7.1. **ood-test is reported once per final system** (`make ood-eval-test`; every run appended to `results/ood/test_log.jsonl`). ood-test has not been run.
- **OOD set** (P3.11, P3.12): Twitter (Kaggle `thoughtvector/customer-support-on-twitter`, **CC BY-NC-SA 4.0**, committed with attribution): inbound thread-openers, `@mentions` stripped (first kept as `brand`), English, ≥ 60 chars, deduped, seeded (4242) 600-candidate pool, pre-labelled by qwen3.8-27b (no reasoning; separate rate bucket). Quotas Technical 45 / Billing 40 / General 40 / Feature 20 / Meeting 10 / Spam 10, but Feature/Meeting/Spam are rare on Twitter (18/1/5) → 149 rows. Enron spam: AUEB server's TLS chain fails verification (not bypassed), so 20 seeded rows from the CC0 Kaggle copy `venky73/spam-mails-dataset` (lower-cased tokenised text). Team-written template for ~40 emails. Only `needs_review=false` rows are scored; reports add a separate **PRELIMINARY** table including pre-labels.

## 8. Routing, SLAs and meetings

- **Rules** (P4.1, `config/routing_rules.yaml`): first match wins; required default last. Conditions: `ingest_status`, `category`, `urgency`, `tier`, `low_confidence`, `possible_spam`, `no_reply`, `min_confidence` (inclusive) / `max_confidence` (exclusive) — contract fields only, so rules work with any models. Actions `mute | queue | reply | schedule`; queues must be declared. Priority 1–4; when omitted from urgency (critical 1, high 2, medium 3, low 4), or 3 without a classification. Shipped order: skipped → human_review P3; Spam → mute; possible spam → `possible_spam` queue (never muted); **critical → human_review P1 (before no-reply, so automated outage alerts are queued)**; no-reply → mute; low_confidence → human_review; Meeting → schedule; Technical/Billing/General → reply; Feature → `product`; default → human_review P3. Hot reload polls the file's sha256 (no fsnotify; works with editors that replace files); an invalid edit is logged once and the old rules stay. YAML decoded with `KnownFields`.
- **No-reply detection** (P4.2), conservative and ordered, first hit is the reason: (1) sender local part noreply/no-reply/do-not-reply/donotreply/mailer-daemon/postmaster/bounce(s)/notification(s)/newsletter(s)/news/marketing/mailer (+ `+tag`); (2) automated subject (`[Automated]`, `Automatic reply`, `Out of office`, `Undeliverable`, …); (3) automated body phrases; (4) newsletter footers (`unsubscribe`, `view in browser`, …); (5) `FYI` subject with no question mark; (6) a bot-like sender (`alerts`, `bot`, `system`, `status`) only together with "automated". A bot-like sender alone isn't enough (`alerts@…` "production database down" stays actionable).
- **SLA + escalation** (P4.3, `config/sla.yaml`: P1 1h / P2 4h / P3 24h / P4 72h, wall-clock): **the clock starts at routing time**, not `received_at`. Muted routes have no SLA. Every poll, open routes past `sla_due_at` get priority −1 and a fresh deadline; at P1 the deadline is re-armed (`sla.breached_p1`), else `sla.escalated`. The update is conditional on `status='open'` and the deadline read, so it can't double-escalate. One current route per ticket, escalated in place; history in `audit_log`. Routing covers skipped tickets and classified accepted ones. One `route.run` audit row per run. Worker order: poll → classify → route → escalate → meetings → replies → outbound → monitoring; a failing step is logged and the next still runs; `-once` exits 1 if any failed; rules hot-reload every 5 s.
- **Meeting extraction** (P4.4a, `POST /extract_meeting`): gpt-oss-120b, JSON mode, temperature 0; relative dates resolved against `received_at`; unparseable, past or > 1-year starts, durations outside 5–480 min and unknown timezones become null with a note. LLM built lazily (503 without `GROQ_API_KEY`). ~520 tokens per extraction. Live check: "Thursday at 3pm" in an email received Tuesday resolved correctly; "whenever works" → start null.
- **Scheduling policy** (P4.4b, `scheduler.DefaultConfig`): Mon–Fri 09:00–17:00 in `GOOGLE_TIMEZONE`; 30-min default duration and slot step; **2 h minimum lead**; 14-day horizon. A requested slot is **booked** only when ≥ 2 h ahead, inside one workday and free; otherwise a **counter-offer** (first free aligned slot after the requested start if busy, else after now + lead; no event created), else **no_slot**. Wall-clock day boundaries keep DST weeks right; one FreeBusy call per request.
- **Google Calendar** (P4.4c): REST v3 `freeBusy` and `events.insert?sendUpdates=all` over OAuth2 (refreshed tokens saved back); installed-app flow with loopback on 127.0.0.1, state check, PKCE S256, offline access, token file 0600.
- **Meeting step** (P4.4d): tickets whose current route action is `schedule` with no `meetings` row (one outcome per ticket). Extraction (60 s timeout) → `Schedule` (sender as attendee, venue as location, "Support call: <subject>"). `not_a_meeting` is stored and the ticket keeps its route. Failures leave it pending. A counter-offer creates no event; the acceptance flow is future work. **`MEETING_CALENDAR`**: `google` (needs `make calendar-auth`), `fake` (in-memory, demo only), `off`; unset → `google` if `GOOGLE_TOKEN_FILE` exists, else `off`.

## 9. RAG

- **KB = WixQA** (P5.1, HF `Wix/WixQA`, **MIT**): 6,221 help-centre articles + expert-written (200) and simulated (200) QA pairs pointing at source articles (chosen over TechQA). The KB is per-deployment content: any docs folder via `python -m rag.kb --folder ...` (Phase 5 review: demo stays in the Wix domain, no custom KB).
  - **Chunking:** h1–h4 split sections; one chunk per section had a median of 79 tokens, so consecutive short sections are packed into ≤ 300 words (~400 tokens) keeping each heading line; a longer section is windowed alone with 45 words (~60 tokens) overlap; overlap never crosses a heading. 13,220 chunks, median 286 tokens, max 400 (within bge's 512; words × 4/3). Embedded text = title + chunk (chunk starts with its heading); images/scripts/styles dropped; list items keep "- ".
  - **Idempotent:** `kb_documents.metadata.sha256` covers chunker version (`packed-v2:300:45`), title, url and text; unchanged articles skipped, changed ones re-chunked with stale chunks deleted. Writes to DATABASE_URL are additive (the KB is product data). Storage: ~66 MB incl. HNSW of the free tier's 500 MB.
- **Retriever** (P5.2): query = `model_input` prefixed with bge's instruction ("Represent this sentence for searching relevant passages: "); cosine top-k over HNSW (`ef_search` 100), k=5. **Hybrid** (`RETRIEVAL_HYBRID=true`): RRF (k=60) of dense top-50 and Postgres full-text top-50 (`websearch_to_tsquery`, `ts_rank_cd`; BM25-like; generated `tsv` column, migration 00008); results keep cosine scores so the floor means the same. **Dense is the default (it beat hybrid on both sets).** Retrieval eval is document-level (gold article among the documents of the top-10 chunks, deduped in rank order). The ml-service holds one psycopg connection behind a lock plus one shared bge-small embedder (max_length 512).
- **Reranker** (P5.6): **rejected as default** (rule: keep only if recall@1 improves ≥ 5 pts without blowing memory). `cross-encoder/ms-marco-MiniLM-L-6-v2` over the dense top-20 lowered recall@1 and tripled latency (results.md); plausible cause: MS MARCO web relevance vs WixQA how-to phrasing. Behind `RETRIEVAL_RERANK=true` (off).
- **Generator** (P5.3, `POST /draft`, gpt-oss-120b, JSON mode, temperature 0): every factual statement ends with [n]; no outside knowledge; **never claim or promise an action** (refund issued, setting changed, escalation) unless a source says so (the SCRIBE failure in `results/examples/ungrounded_hallucination_01.md`); when sources don't answer, say so and ask for what's missing; no placeholders; sign-off "The Support Team". Tone from urgency + a per-category hint. **Draft → constrained refine:** the refiner may change clarity and tone only; if its [n] set differs, the refined text is discarded (noted). `[n]` outside 1..len(chunks) removed and reported in `invalid_citations`; `citations` = cited chunk ids in first-cited order. No chunks → HTTP 422.
- **Faithfulness gate** (P5.4, `POST /verify`): **one judge call per draft** (qwen3.8-27b, a different family from the drafter, temperature 0, JSON) splits claims and judges support: `{claims: [{claim, cited, supported, reason}]}`. Greetings, sign-offs, empathy and questions aren't claims; an action claim is supported only if a source says it. `faithfulness_score` = supported / all, **1.0 when there are no factual claims** (still agent-reviewed). **Abstain** (`config/grounding.yaml`): no chunks; best retrieval cosine < **0.7177**; score < **0.9**; reason and unsupported claims recorded. Floor and empty checks run before the judge (no tokens). **Floor from data:** 5% quantile of best top-5 cosine over 400 answerable WixQA questions (95% pass); 88.8% of 400 Tobi-Bueck val tickets fall below it (out of KB). `/retrieve` returns `retrieval_floor` + `below_floor`. Judge responses cached by sha256(model + messages) in `datasets/raw/llm_cache/judge/`. A draft whose claim list overflows max_tokens is judged in two halves (`split_halves`, up to depth 2) and pooled, live and in eval.
- **Reply step (Go, P5.5):** tickets whose current route action is `reply` with no `reply_drafts` row (10 per run; up to 3 LLM calls each). Retrieve (k=5); **no chunks or below floor → stored abstained without drafting or judging**. Otherwise draft → verify → store the draft with abstain reason, retrieval max score and mode, per-claim judgements, retrieved chunk ids. **Abstained → `Routes.Reassign` to `human_review`** (action `queue`, reason appended, priority/SLA kept). Grounded drafts wait for agent review; nothing is sent automatically. An ml-service failure leaves the ticket pending. ml client timeout 120 s.

## 10. Review, API, UI and outbound

- **Review data rules** (P6.1a): inbox order = route priority (1 first), then SLA deadline, then newest; unrouted last. `status` filter = route status `open | resolved | unrouted`. **Draft transitions** (conditional UPDATE; disallowed → `ErrConflict` → HTTP 409): approve from `grounded`, or from an `abstained` draft an agent edited (non-empty body), setting the idempotency key `draft-<id>`; edit only `grounded`/`abstained`, setting `edited=true`; reject anything not yet sent (and not mid-send). Reviewer, note and time recorded. **Reject also moves the ticket to `human_review`** (reason `draft_rejected`, same transaction, audited) (Phase 6 review). **Abstain rate** = drafts with `abstain_reason` / all drafts; average faithfulness over judged drafts only.
- **API conventions** (P6.1b, spec `docs/openapi.yaml`, a test checks every route is documented): paths exactly the spec's (no version prefix). `GET /health` public; everything else needs `API_KEY` (`X-API-Key` or `Authorization: Bearer`, constant-time compare); no key configured → 401 everywhere; `cmd/api` refuses to start with an empty or `change-me` key. Errors `{"error": {"code", "message"}}` with codes bad_request / unauthorized / not_found / conflict / payload_too_large / internal. Validation: category in taxonomy, urgency in scale, status in open/resolved/unrouted, limit 1–200, UUID ids, reviewer required, edit needs a body. `POST /ingest/csv`: multipart field `file`, ≤ 5 MiB, `.csv` only, stored as `datasets/out/uploads/<UTC time>-<random>.csv` (never the client's name), ingested via `preprocess.Ingestor`. Review actions write `draft.approved|rejected|edited` audit rows with the reviewer as actor.
- **UI** (P6.2): plain HTML/CSS/JS, no build step, embedded via `go:embed`; hash routes `#/inbox`, `#/tickets/<id>`, `#/dashboard`. **Security:** ticket and draft text only via `textContent` (a test fails on HTML sinks in `app.js`); CSP `default-src 'self'; script-src 'self'`, `nosniff`, `no-referrer`, `frame-ancestors 'none'`; chunk URLs linked only when http(s), `noopener noreferrer`. API key and reviewer name in localStorage; 401 → key prompt. `[n]` maps to the exact chunk the drafter saw (the API returns the number per chunk). Buttons mirror store transitions; the server enforces them. Dashboard tiles/bars come from a pure `dashboard.js` model. Demo-only **"eligible for auto-send"** badge (grounded, unedited, faithfulness 1.0, above floor); human approval is mandatory.
- **Outbound** (P6.3): **exactly one send per approval, never a blind resend.** Claim first (conditional `UPDATE … FOR UPDATE SKIP LOCKED` sets `send_started_at`); call the adapter of `Ticket.Source`; success → `sent`, `sent_at`, route `resolved` (+ `resolved_at`) in one transaction; known adapter error → `send_error`, claim released, retried up to 5 attempts. **A claim older than the 10-min lease = died mid-send → flagged `send outcome unknown` (`reply.send_unknown`), never resent automatically.** Adapter success but failed recording leaves the claim for the lease rule. Idempotency key `draft-<id>` passed to adapters: CSV writes a key at most once (`IdempotencyKey` column; an old-format `replies.csv` is an error); email `Message-ID: <draft-<id>@domain>`; Zendesk `Idempotency-Key` header (support unverified; the claim protocol is the guarantee). A ticket whose source isn't enabled fails with a clear `send_error`.

## 11. Monitoring (P7.3)

- **PSI reference = val category shares, Spam included** (categorised rows of `spam_val`: Technical 0.5306, Billing 0.1306, Feature 0.0991, General 0.1629, Spam 0.0609, Meeting 0.0159; `train` is capped so its shares aren't natural). PSI = Σ (p−q)·ln(p/q), shares floored at 1e-4; current = each ticket's latest classification that UTC day. **Alert at PSI > 0.2**; none below 30 classified tickets.
- **Latency:** the worker times every ml-service call (retries included) via `mlclient.Client.Observe`, buffers, one COPY per cycle into `stage_timings`. `ingest_to_classified` / `ingest_to_draft` from row timestamps; p50/p95 via `percentile_cont`.
- **SLA breach rate** = routes created that day with an SLA resolved after the deadline or still open past it; the job recomputes yesterday and today (UTC). `routes.resolved_at` added (earlier rows backfilled from `updated_at`).
- **Abstain rate** as in section 10. Results in `metrics_daily`, served by `GET /metrics/daily?days=`.

## 13. LLM usage and Groq limits

- **Client** (P0.3a): plain httpx against the OpenAI-compatible endpoint (not the `groq` SDK) for full retry control: 429/5xx/transport back off exponentially with jitter (≤ 5 retries, 30 s cap) honouring `Retry-After`; other 4xx fail immediately; sleep/transport injectable. 429 bodies keep 500 characters with the org id redacted, so the limit name (e.g. "tokens per day (TPD)") survives (P7.2d).
- **Roles** (`build_llm(settings, role)`): drafter `openai/gpt-oss-120b`, reasoning low. Judge configured separately (`JUDGE_MODEL`, `JUDGE_BASE_URL`, `JUDGE_API_KEY`, `JUDGE_REASONING_EFFORT`), default `qwen/qwen3.8-27b` (different family, less self-agreement). Reasoning comes back in a separate `reasoning` field, so `content` is clean JSON; qwen3 doesn't reason when effort is omitted.
- **Judge settings** (P5.4, supersedes the earlier "medium"): qwen is capped at **1,000 output tokens/minute**, so `JUDGE_MAX_TOKENS=1000` and `JUDGE_REASONING_EFFORT` empty (reasoning off); with reasoning low, 726 of 843 output tokens were reasoning and long drafts were cut off. Throughput ≈ one draft per minute. Reasoning-off accuracy is checked by P7.2's κ.
- **Limits:** `max_tokens` default 4096 (`LLM_MAX_TOKENS`); `finish_reason=length` raises instead of returning truncated JSON. Groq JSON mode can fail server-side with HTTP 400 `json_validate_failed` → `JSONModeError`, treated as a bad attempt (retried) by the drafter, judge, meeting extraction and style-aug. Usage logged per call and accumulated in `GroqLLM.usage`.
- **Free tier on this key:** 1,000 requests/day, 8,000 tokens/minute, and **200,000 tokens/day (rolling) for gpt-oss-120b, shared by every gpt-oss job.**
- **Token budget priority** (Phase 4 review): P7.2 first (its judge runs resumable and cached across days), then style-aug on leftover budget, as is the deferred live `/extract_meeting` check. Any LLM batch job must be cached and resumable.
